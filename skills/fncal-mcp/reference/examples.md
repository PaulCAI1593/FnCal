# 用法示例

四个真实场景，含调用与「该怎么跟人说」。所有时间按用户时区自行换算成 ISO 8601。

## 1 「我今天有什么？」

```json
tools/call list_events { "from": "2026-10-29T00:00:00+08:00", "to": "2026-10-30T00:00:00+08:00" }
```

回话方式：按时间排序，只念有内容的（标题 + 时间 + 地点），跨天事件合并成一条。

> 今天三件事：10:00 周会（三楼会议室）、14:30 和合肥那边对需求、20:00 健身。

不要念 `busy: true`、不要念 uid、不要念内部 id。

## 2 「下周三下午给我约个 1 小时的会，跟合肥」

1. `list_calendars` → 找到 `access: "write"` 的日历 id。
2. `find_free_slots { "from": "2026-11-04T13:00:00+08:00", "to": "2026-11-04T18:00:00+08:00", "minMinutes": 60 }`
3. `create_event { "calendarId": "my-calendar", "title": "和合肥对需求", "start": "2026-11-04T14:00:00+08:00", "end": "2026-11-04T15:00:00+08:00", "location": "线上", "note": "按你周三下午的习惯排的" }`

结果 `applied: false` → 回话：

> 已提交待确认：11/4 周三 14:00–15:00「和合肥对需求」。13:00–14:00 你有别的会，所以没排。请在 FnCal 里点一下确认。

结果 `applied: true`（直接写入模式）→ 回话：「11/4 周三 14:00–15:00 已加好，线上。」

## 3 「把明天的评审往后挪一小时」

1. `list_events` 找到 uid 与当前 etag。
2. `update_event { "uid": "…", "ifMatch": "<etag>", "start": "…", "end": "…", "note": "挪到 11:00" }`
3. 如果 `409 stale`：说明期间被改过（网页或手机）。重新 `get_event`，再提一次，并告诉人「中间有人改过，我按最新的又提了一次」。

## 4 「把那个已经取消的会删了」

```json
tools/call delete_event { "uid": "…", "note": "会议已取消" }
```

回话取决于这条凭据的**删除方式**（与「新建、修改」是两组独立设置）：

- 提案模式（默认）：删除只是提案，等人确认。

> 已生成删除提案，请在 FnCal 里确认；删除不会由我直接执行。

- 回收站模式：立即删除并进入回收站，保留期内可恢复。此时不要再说「无法撤销」。

> 已删除，并移到 FnCal 回收站；保留期内可以在 FnCal 里恢复，我这边没有恢复入口。

## 5 只读凭据 / 字段被遮时怎么答

- `tools/list` 里没有写工具 → 不要尝试、不要换名字猜。直接说：「这把 AI 凭据是只读的，要我改的话，请在 设置 → AI 里把对应日历放成「读写」。」
- 写工具在、但目标日历是「只读」档 → 工具会回 `该日历只有「只读」权限：请在 FnCal 的 AI 凭据里把这个日历改成「读写」后再试。` 原句告诉用户，别说「日历不存在」。
- 写入的时间在凭据时间窗之外 → 工具会回 `这个时间在你的凭据时间窗外：请在 FnCal 里放宽这个凭据的时间窗，或换一个窗口内的时间。` 不要重复重试同一时间。
- 事件里没有 `description` 键 → 不要说「这件事没有备注」，说「备注字段没有授权给我看」。
- `list_calendars` 少了一个日历 → 不要问「是不是还有别的日历」，也不要猜名字；按你能看到的回答。
- 问的是一个你确定存在、却返回 not found 的事件 → 很可能是时间窗之外（默认只给过去 7 天、未来 90 天）。可以说：「这超出了这个 AI 凭据能看的时间范围。」

## 6 代办批准：弹窗点击，或审批链接（列表页）

FnCal 0.4.22 起有两条确认路径：支持 elicitation 的客户端在调用中弹 FnCal 自己的确认框；没有弹窗的客户端返回**审批链接**（`approvalUrl`，10 分钟内有效，绑定的每条提案只能处理一次）。页面就是提案列表的样子：顶部「刷新」、剩余 2 条以上才有「全部批准 / 全部拒绝」，每条卡片自带「批准 / 拒绝」。凭据设了 4 位 PIN 时，页面先要求输 PIN（四个格子）——**永远不要向用户索取 PIN**。服务端不把对话里的「同意」当授权，也不认 `confirmed`（已废弃）。

```json
tools/call approve_proposal { "id": "…" }
// 客户端没有 elicitation 弹窗能力 → isError
{ "code": "approval_requires_ui", "tool": "approve_proposal", "reason": "no_elicitation",
  "total": 1, "proposalId": "…",
  "message": "请在浏览器打开上面的链接确认；未确认前未执行。",
  "approvalUrl": "http://<host>/a/<token>", "pinRequired": false, "expiresIn": 600,
  "ui": { "panel": "proposals" } }
```

1. 无弹窗客户端（如 Claude Desktop 目前）：不要重试、不要带 `confirmed`、不要索取 PIN，把 `message` 与 `approvalUrl` 原样给用户，请他在浏览器打开链接确认（有 PIN 他自己输）。
2. 有弹窗的客户端：调用中 FnCal 弹「批准 / 拒绝 / 取消」，用户点了才继续；`{declined:true}` 与 `{cancelled:true}` 都不改数据。
3. 永远不要自己替用户点「同意」，也不要把「他说批准了」当成弹窗结果。

## 7 「把待批的提案处理一下」

用户：把待批的提案处理一下。（2 条以上）

助手：调 `decide_proposals { "action": "approve" }`，不要自己批量。
- 有弹窗：FnCal 弹「全部批准（5 条 / 含 1 条删除）」/「逐条审批」/「取消」，用户点了才继续；选全部后回话「已批准 4 条，1 条失败（已过期）；那 1 条删除已生效，无法恢复」。
- 无弹窗：回 `approval_requires_ui`（`total`、`deleteCount`、`message`、`approvalUrl`、`ui.panel="proposals"`），一条都不执行。把 `message` 与链接给用户：链接页列出这一批，可以逐条点，也可以「全部批准 / 全部拒绝」，删除类会写明能否恢复。不要问「全部还是逐条」，这边执行不了。

## 8 只有一条待批时：不问模式

用户：把待批的提案处理一下。（只有 1 条）

助手：调 `decide_proposals { "action": "approve" }`——不要问「全部批准还是逐条审批」。
- 有弹窗：FnCal 直接弹「批准（修改）「周会」」/「拒绝」/「取消」，用户点了才继续。
- 无弹窗：回 `approval_requires_ui`、`total: 1`、`proposalId`、`message` 与 `approvalUrl`；把链接给用户（页面只有这一条，有 PIN 他自己输），不要重试、不要带 `confirmed`、不要索取 PIN。

助手回话（有弹窗且用户点了批准）：「已批准 1 条，日历已更新。」——不要说成「全部批准」，也不要替用户决定。
