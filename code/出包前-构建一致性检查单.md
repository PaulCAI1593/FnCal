# FnCal 出包前：构建一致性检查单（固定三步）

适用：所有带前端改动的版本。起因 0.8.49 打包早于最后两处前端改动（14:26 打包 / 14:35 改 `app.js`、`account-dialog.js`），用户在包里遇到 `e.syncCalendar is not a function`，而源码里已有兜底。

## 三步（缺一步不出包）

1. `rm -rf code/web/dist`：不复用任何旧产物。
2. `cd code/web && npm run build`（cwd 必须是 `code/web`；不要在 `code/` 下用 `--prefix` 代替）。
3. **一致性证明**二选一，结果写进当版记录：
   - 用当前源码另建一份（如 `web/build-tmp/verify-dist-<ver>`）重建，与 `web/dist` 逐个 assets 比 SHA-256，全部相同才算过；
   - 至少确认包内含有**本版新增**的标识串（新函数名、新文案、新 class），并给出命中文件与命中数。

之后才是 `stamp-version.mjs` → `assemble.mjs` → `audit-zero-cloud.mjs` → `make-fpk.mjs` → `verify-fpk`（带 `--port-entry --url-entry`）。

## 检查串时的两个坑

- 前端按内容哈希分块：`account-dialog.js` 打进 `assets/date-popover-*.js`，不在 `index-*.js`。**grep 要覆盖 `assets/*.js` 全部**，别只查 `index-*.js`（0.8.49 那次「包内没有兜底文案」的判断就是这么误判的）。
- 判断新旧不能靠「某个文案在不在」：i18n 分块里常有旧版就存在的句子。用「本版新增标识」或重建逐字节比对。
- 记录里写证据要写清「哪个文件、几处、什么命令」，不写「应该有」。

## 版本号

同一版本号不得重打包；只要包字节变化就升号。包已交用户机器后再改，同样升号（0.8.49 → 0.8.50 即此例）。

## 回归位清单（离线层白名单漏项）

`main.js` 的实际链路是 `createStore(createOfflineKv(createRestKv()))`。离线层 `web/src/js/offline-store.js` 的 `delegated` 是**白名单**：不在名单里的方法，组装后的 store 上就是 undefined，调用即抛英文 TypeError，而单测若直接 mock store 就抓不到。

已发生三次同型事故，每次都必须由 `web/tests/offline-store-delegation.test.js` 锁住：

| 方法 | 事故版本 | 现象 |
| --- | --- | --- |
| `clearCalendar` | 0.2.3 | 「清空」只弹失败，事件一个没删 |
| `syncCalendar` | 0.8.49 | 点「立即同步」报 `e.syncCalendar is not a function` |
| `testSubscription` | 0.8.49（同批） | 订阅「测试地址」同链路不可用 |

新增任何后端方法（含批量 API、导入导出）时，三处一起改：`kv-rest.js` 实现 + `offline-store.js` 名单 + `offline-store-delegation.test.js` 的 `DELEGATED`。

**反向缺口**：现有测试只能证明「名单里的名字在 REST 层存在」，不能发现「REST 有、名单漏」。名单漏项只能靠出包前人工比对两边的导出清单——`kv-rest.js` 的 return 与 `offline-store.js` 的 `delegated` 名单逐项对照，差异项要么补名单，要么在代码里写明「故意不透传」的理由。
